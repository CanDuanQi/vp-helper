# VP Helper

Ubuntu 上的 XCPC 虚拟参赛终端助手，支持 QOJ、Codeforces ICPC 比赛和 Codeforces Gym。上方显示成绩与完整提交记录，下方保留比赛目录中的普通 shell。

当前版本：0.1.16+cdq.7（CanDuanQi 修改版，基于上游 0.1.16）。

## 本 Fork 的修改

原作者与来源：[thedyingkai/vp-helper](https://github.com/thedyingkai/vp-helper)。保留其提交历史、作者信息和 `third_party/` 内的组件来源、兼容补丁与许可证。

- QOJ、Codeforces 和 Gym 以平台确认的 **ICPC 计分规则**为准，不再要求标题带有年份、赛站和 Reg/Inv/Pro。CF / IOI 计分仍会拒绝；平台原生 VP 和赛长要求不变，PDF 题面改为按需下载。
- 正式 ICPC / CCPC 标准赛事仍采用原目录名称和原赛校验、回放、实时排名、奖项、封榜及题号揭示机制。
- 非标准赛事目录采用“平台 ID 标题”，例如 `QOJ 2565 比赛标题`，清理路径分隔符等特殊字符并限制长度；不同 ID 不会因同名比赛而共用提交配置。题面下载、`contest.json`、个人 ICPC 成绩、提交记录及补题标记沿用原有流程。
- QOJ 标题优先读取比赛内容区，避免把站点标志 `QOJ.ac` 当成比赛名称。单题 PDF 支持 `download.php?type=statement` 内嵌链接，即使 URL 不含 `.pdf` 也可下载；下载后仍验证 PDF 文件头。
- 准备新比赛时询问 `Download problem PDFs? (y/N):`，回车默认跳过，输入 `y` 才下载；全局 `download_pdfs` 配置可固定默认行为。恢复已有 VP 不重复询问，不删除已有题面和代码。
- 修复 QOJ 自动启动：首页的 Start 按钮只进入规则确认页；程序通过 GET 取得最终报名表单，再发送唯一一次启动 POST。支持登记延迟和超时后的只读核验，按表头解析原站开始时间及个人时长，并防止再次运行时重复启动。
- 没有可靠原赛数据时，尝试 QOJ 当前原站榜单并明确显示“QOJ 参考排名”；QOJ 数据也不可用时排名和统计显示 `—`，奖项保持 `Unknown`。不会根据标题或备用榜单编造原赛资格、奖牌名额或提交回放。个人成绩及提交记录仍更新。
- 内置 QOJ 提交器对 `.cpp`、`.cc` 默认使用 `C++23`；`.py` 仍使用 `PyPy3`。使用方法仍为 `submit A.cpp`，语言会显示在提交确认信息中。
- QOJ 提交遵循题目页跳转后的实际提交表单地址（包括 `/statement/zh_cn` 等语言页面），只使用该表单的 Token。每次最多上传一次；回执延迟时仅以 GET 查询新提交编号，明确拒绝会显示脱敏原因，无法确认时提示先查网页，避免重复提交。
- Firefox 自动配置识别新增 `~/.mozilla/firefox-esr/`，兼容 `profiles.ini` 的相对和绝对路径、默认配置及 sudo 原用户识别。
- 增加 `vp --version` 和无需 sudo 的用户目录安装，方便确认正在使用本 Fork。

使用方式不变，例如下列命令会在你主动执行时启动或恢复原站 VP（测试不会执行这些命令）：

```bash
vp qoj 2565
vp qoj 4616
```

比赛仍须在平台上提供 ICPC 赛制、赛长和原生 VP；跳过下载时不要求平台提供 PDF，放宽名称不会绕过平台的登录或参赛条件。

## 安装

支持 Ubuntu 22.04 / 24.04，随仓库提供 Linux x86_64 的独立 Python 3.12 运行时与依赖 wheels。安装器使用隔离环境，保留系统 Python。

```bash
git clone https://github.com/CanDuanQi/vp-helper.git
cd vp-helper
bash install.sh
```

安装后可在任意目录使用 `vp` 和 `submit`。Python 运行时与依赖可从仓库离线安装；系统未安装 tmux 时，安装器通过 apt 安装 tmux。

更新 Git 克隆的仓库后，重新运行安装器：

```bash
git pull --ff-only
bash install.sh
```

使用 ZIP 安装时，重新下载并解压最新版，在新目录内运行 `bash install.sh`。全局 `vp` 使用 `/opt/vp-helper/current` 中的安装副本，只更新源码目录不会更新已安装的命令。

### 用户目录安装（不需要 sudo）

本机已有 Python 3.12+（含 venv/ensurepip）和 tmux 时，可使用仓库内 wheels 离线安装：

```bash
bash install-user.sh
hash -r
command -v vp
vp --version
```

安装目录为 `${XDG_DATA_HOME:-~/.local/share}/vp-helper/`，入口为 `~/.local/bin/vp` 和 `~/.local/bin/submit`。请让 `~/.local/bin` 位于 PATH 最前；它们将优先于全局同名命令。已有全局 `/usr/local/bin/vp` 和 DOMjudge 等其他 `submit` 程序保留，可通过其绝对路径使用。若用户入口已有其他文件或非本安装器管理的链接，安装器会退出而不覆盖。已有账号、比赛、历史文件保留，原有 `submit_script` 显式配置也继续生效。

各次安装保留独立 release，只有依赖安装和检查成功后才切换 `current`。提交器使用当前 VP 的安装环境，支持用户目录和系统目录两种安装。更新代码后重新执行同一个安装器；旧的 `/opt` 版本不会因用户安装被修改。

确认安装路径及版本：

```bash
type -a vp submit
readlink -f "$(command -v vp)"
vp --version  # VP Helper 0.1.16+cdq.7
```

## 使用

将 `ID` 替换为对应平台的数字比赛编号：

```text
vp cf ID
vp qoj ID
vp gym ID
```

例如：

```bash
vp qoj 3169
submit A.cpp
vp history
```

也支持 `vp CONTEST_URL`。计分范围限定为 ICPC；普通 Codeforces Round 的 CF / IOI 计分会在开赛前被拒绝。

先在 Ubuntu 的 Firefox 登录 QOJ 或 Codeforces，再运行比赛命令。`vp` 和内置 `submit` 自动读取 Firefox 的登录状态，并通过网站导航中的登录用户核对账号；未填写 handle 时也可以从已验证的浏览器登录自动取得。Codeforces / Gym 的 API key 与 API secret 仍在首次使用时配置。配置保存在 `~/.config/vp/config.json`，权限为 600；也可以参考 `config.example.json` 填写。`cf` 与 `gym` 默认共用 Codeforces 配置。

自动读取支持 Firefox 的旧目录 `~/.mozilla/firefox`、ESR 目录 `~/.mozilla/firefox-esr/`、XDG 目录（默认 `~/.config/mozilla/firefox`，也支持自定义 `XDG_CONFIG_HOME`）、Ubuntu Snap 和 Flatpak 目录，读取该网站的持久 Cookie 和最新会话恢复记录；其他网站及容器、隐私会话不参与导入。程序只读取浏览器文件。验证通过后将登录数据保存到本地配置，账号不匹配或网络验证失败时保留原配置。GET 遇到登录过期会重新读取并验证一次；启动 VP 和提交代码的 POST 不自动重发。Firefox 尚未保存新会话时稍候再运行命令，或登录时勾选“记住我”。

登录过期时，在 Firefox 重新登录同一个账号，再运行原命令即可，无需复制 Cookie。多 Firefox 配置可在对应平台账号中指定 `firefox_profile` 为该 profile 的完整路径；sudo 启动时默认使用原普通用户的 Firefox。root 与普通用户的应用配置仍分别保存，root 使用 `/root/.config/vp/config.json`，普通用户使用自己的 `~/.config/vp/config.json`。

首次导入失败会分别显示配置目录未找到、Cookie 读取失败、登录账号不符、HTTP 错误或网络验证失败等原因，不输出 Cookie 值。自定义目录可从已登录的 Firefox 的 `about:support` 页面复制“Profile Directory / 配置文件夹”，填入对应账号的 `firefox_profile`；不要填写缓存目录。QOJ 的 `handle` 区分大小写。网页已开始的 VP 在登录恢复后可以通过原命令接续，沿用原站开始时间。

已有手动配置也可继续使用。要固定使用手动 Cookie，在账号中设置 `"cookie_source": "manual"`；填写 `cookie` 时只复制请求中 `Cookie` 的值，省略 `Cookie:` 标签和其他请求头。

每场比赛在桌面共用一个目录，例如 `2024 ICPC Nanjing Reg`。再次进入保留已有代码、题面和输入数据，更新提交配置；题面仅在准备比赛时按下载选项获取，各次 VP 的开始时间和成绩状态独立保存。`submit A.cpp` 在对应比赛目录内运行。

请用同一个 Linux 用户运行 `vp` 和 `submit`；root 与普通用户的桌面目录和 VP 状态互相独立。QOJ 提交器会在当前目录、源码所在目录及其上级目录查找 `contest.json`，因此也支持从子目录提交或在别处指定源码路径。当前目录与源码绑定不同比赛、账号或题号时会要求切换到源码的比赛目录；同场同账号的配置以当前目录为准。找不到配置时给出恢复指引。重新运行同一场 `vp` 命令会补齐或刷新提交配置，沿用已经确认的原站开始时间。

### 按需下载题面 PDF

QOJ、CF、Gym 使用同一选项。准备新比赛且尚未设置偏好时，会询问：

```text
Download problem PDFs? (y/N):
```

直接回车或输入 `n` 跳过，仅输入 `y`（不区分大小写）才下载。本次回答不会自动写入配置；下场新比赛仍会询问。恢复本地已有 VP 时不重复询问，正常恢复分支也不会重新查找或下载 PDF。

若希望固定行为，在 `~/.config/vp/config.json` 的**顶层**添加 `download_pdfs`，保留原有账号配置。下面仅展示新增字段：

```json
{
  "download_pdfs": false
}
```

`false` 是默认行为：跳过下载且不再询问；设置为 `true` 时自动下载且不再询问。必须使用 JSON 布尔值，不能填写字符串 `"false"`。删除该字段可恢复询问。`config.example.json` 已包含 `false`。

跳过下载时也跳过 PDF 附件与单题页面查找，不会因平台未提供 PDF 而停止准备；比赛目录、提交配置、原站自动 VP 和评分面板照常工作。不会删除已有的 `A.pdf`、`B.pdf`、代码或其他文件；选择下载时也保留已有同名文件，只下载缺失的题面。当前运行的监控进程无需因这个选项重启。

## 成绩与界面

- `vp` 创建比赛目录和提交配置，并按选择下载题面后，在现有账号上启动并验证原站 VP，以平台开始时间计时。
- QOJ 无需提前在网页启动 VP。`vp qoj ID` 会先查询本账号登记；已有正在进行的 VP 直接恢复，否则自动 GET `/virtual/register` 读取最终确认表单，携带该表单的 CSRF Token 和提交按钮发送一次启动 POST。首页的 `regvir` 入口不会被误当作已完成报名；旧站点没有确认页时仍支持直接启动。
- 启动后仅 GET 查询登记记录，等待间隔为 0、2、3、5、8、12 秒（累计等待 30 秒，另计网络耗时）。开始时间只取原站 `<time datetime>` 或登记时间文本；个人时长优先取匹配的原站 Duration。三列 VP 身份表和五列时间/时长表分别解析，可跨分页关联。账号不符、表头或时间解析失败均会明确报错，不会伪造本地开始时间。
- 发送启动请求前，在用户状态目录（默认 `~/.local/state/vp/`）保存 `qoj-start-*.json` 待确认记录，仅包含比赛 URL、账号、先前原站开始时间及标准请求错误，不保存 Cookie 或 CSRF Token。请求超时、程序中断或登记暂未出现时保留该记录；再次执行原命令只读核验，找到新原站记录后自动恢复并移除保护记录。明确的表单拒绝会显示原因；307/308 重定向不会重发 POST。
- 若待确认状态持续存在，输出会区分请求错误、登记查询/解析错误和未出现新登记三种原因，并给出保护文件路径。不要反复删除文件重试：只有独立确认原站没有开启 VP 后，才可清除该场待确认记录以允许新的自动启动请求。保护期间不需要手动在网页开赛。
- 按正式参赛资格计算排名，排除打星队与其他 VP；解题数和罚时相同共享名次，最后 AC 用时只决定展示顺序。
- 奖项采用原赛明确配置。资格、规则或榜单完整性无法验证时，保留未知结果。
- `rank` 列保持在成绩表左侧，排名和奖项在同一格内分两行显示，例如上行 `=47`、下行 `Silver Prize`。
- 内置 submit 在服务器确认新提交编号后立即通知面板显示 `PENDING`，随后用平台判定替换；本人提交与榜单查询独立执行。
- QOJ 的 0 分提交会读取详情区的测试点判定，区分 WA、CE、RE 等结果；前面通过的测试点不会覆盖后面的失败。详情暂时无法读取时显示 `RESULT UNAVAILABLE`，按退避间隔重查，并继续更新其他提交。影响罚时的结果未确认时，罚时与排名暂不显示确定值。
- 提交记录按时间从新到旧完整展开，`practice` 标注紧贴判定。5 小时后的补题不计入比赛成绩，未通过显示橙色，通过显示紫色。
- 空白、标题与提交列表继承终端默认背景，支持终端自身的透明效果。
- 最终成绩保存到桌面的 `vp_history.csv`。
- `vp history` 增加 `gold`、`silver`、`bronze` 三列，显示原赛正式队终榜的金、银、铜线。每格上行是过题数/罚时，下行是名次界限，例如 `9/1200` 与 `(≤30)`；并列成绩使用相同分界，打星队不计入奖线。比赛完成后保存奖线，旧记录从本地 VP 状态和已核验的原赛缓存补齐。只有奖项名额时过题数/罚时显示 `—`，资格或数据缺失时整格显示 `—`。历史查询不联网，也不改写原有 CSV。

在上方面板用方向键、`PgUp` / `PgDn`、`Home` / `End` 或鼠标滚轮查看提交。`Ctrl+B`、`D` 脱离 tmux 后继续同步；再次运行同一场比赛命令可恢复。按 `q` 关闭评分面板。

QOJ 已完成真实账号联调，包括南京与香港的正式排名、奖项和提交记录。CF / Gym 的账号流程需要已有登录会话和 API 凭据；请按实际平台状态核实。

## 赛时排名与统计

首次运行比赛命令时，程序根据平台 ID 读取比赛信息，自动获取该场原赛资格、榜单和提交记录。有完整原赛提交记录时，先用它重算终榜，与平台每支队伍的每题结果和罚时核对，再按 VP 当前时间每秒回放原赛成绩，计算当前排名与统计。QOJ 使用 XCPCIO 或 SRK 原赛记录；CF 原生参赛队伍使用官方 API 提交记录，导入 ghost 仍须匹配原赛资格和记录。

有待判提交时，在上一轮查询返回后约 2 秒再次查询本人判定；其余时间约 5 秒，网络故障时退避重试。平台榜单约 30 秒重新核对；这些间隔不包含网络耗时。CF 请求统一遵守 API 限速。

QOJ 在 VP 进行中返回的账号榜单已经按当前时间截断，程序使用不携带登录凭据的独立会话读取公开完整终榜来校验回放。档案时间窗口或 QOJ 导入时间与原站 VP 有差异时，分别处理；只有统一时间偏移后的全部终榜结果一致，才接受时间对齐。本人计时和补题分界仍按 QOJ 原站的 VP 时长。导出记录中的管理员测试提交不属于参赛队伍，不计入回放。正式与打星队伍的每题结果仍须和原站终榜逐一一致，才会显示实时排名与统计。

- `submitted`：首次通过前的有效计分提交次数，含待判。
- `attempted`：有有效尝试的正式队伍数。
- `accepted`：通过的正式队伍数。

严格原赛模式的统计包含本人赛内提交，排除打星和赛后补题；编译错误按本场计分规则处理。封榜时公开统计隐藏冻结后的结果，rank 显示 `?`，当前 VP 的原站解封后恢复。缺少资格数据或完整事件记录时，面板显示具体原因；只有终榜时不据此推演原赛赛时排名或统计，可以尝试下面的 QOJ 参考快照。奖项只使用明确的原赛奖牌配置。

2026 年起的 CCPC 区域赛自动启用题号揭示：某题被 50 支不同的原赛队伍通过后，才在公开统计中显示题号，正式队和打星队一并计数，当前 VP 不参与这个阈值。排名、奖项和上面的三项公开统计仍按正式参赛资格计算。尚未揭示的题号及对应统计显示为 `?`，匿名列集中排列，避免从 A–M 的位置推断题号。本人每题成绩与提交记录仍按实际题号显示。到原站规定的封榜时刻，所有题号同时揭示，公开统计固定在封榜前，原站解封后恢复完整结果。

例如 `vp qoj 4582` 会识别为 `2026 CCPC Changchun Reg`，采用 5 小时赛长、4 小时封榜。比赛名称中的 `Site` 及中英文双语标题均可识别；其他人的较短 rated VP 时长不再覆盖公开比赛时长。QOJ 目前仍以传统 ICPC 规则运行该场原站 VP，题号揭示由本地面板模拟。

### QOJ 参考快照

XCPCIO / SRK 的资格、终榜及原赛事件验证仍优先执行。只有无法得到可靠原赛参考时，才读取本轮已获取的 QOJ 榜单，显示“QOJ 参考排名”；后续恢复可靠原赛数据时自动切回。QOJ 备用数据不会被标为原赛终榜完整、原赛统计完整或已验证的提交回放，也不会写入原赛资格与事件缓存。

参考排名采用 QOJ 自己的身份分类，排除所有 VP，合并 QOJ 正式账号及正式导入队伍；不能据此区分现场区域赛与 UCUP 等正式参赛。打星/非正式队伍在参考榜单中以 `*` 标记，不计入排名和统计。QOJ 的 `submitted`、`attempted`、`accepted` 仅从这些正式非 VP 队伍的可见每题结果计算，不再加入当前 VP 的个人提交。个人解题数、罚时和提交记录单独更新。

个人成绩表下方的提交记录之后，附有可滚动的“QOJ 参考榜单”，展示队伍可见成绩、每题通过/错误尝试和解题分钟。使用方向键、PgUp/PgDn 或 Home/End 查看。榜单是约 30 秒刷新一次的原站快照，可能按当前 VP 时间截断，也可能被封榜；它既不是完整原赛终榜，也不是按原赛提交事件逐秒复算的回放。

封榜时直接使用本轮 QOJ 公开分数数组：保留已有 AC、通过分钟、错误次数、公开过题数、罚时和参考排名；只将原站标记隐藏的单元格显示为 `?N`，次数按 QOJ 前端的 `col[3] + 1` 计算。问号不计为 AC 或罚时，不会因为某个单元格存在隐藏结果就丢弃整队或整张榜。程序封榜后首次打开或重启，也能从当前页面恢复公开成绩，无须封榜前运行过本程序或保存过本地榜单缓存。

`accepted` 统计仅计入已公开的 AC；`submitted`、`attempted` 是当前公开尝试统计，包含网页已公开的 `?N` 次数，不泄露隐藏判定。QOJ 没有把 `?N` 拆分为封榜前失败次数和封榜后隐藏次数，因此这些数字不能称为“纯封榜前提交数”。本人个人行仍可显示本人全部已知成绩，但封榜参考名次按本人的公开成绩计算，封榜后的私有 AC 不会提前提高公开参考名次。原站解封后恢复完整成绩和统计。

若收到明确带有冻结时刻之后时间、却未标记隐藏的结果，只将对应单元格标为未知，不把它当成封榜前成绩；保留其他可确认的单元格和队伍成绩，受影响的总成绩、名次或题目统计显示未知。查询失败、身份不明、题号不符、部分分或总分/罚时校验失败时，也不会猜测成绩。奖项始终保持 `Unknown`，除非恢复了原有严格原赛数据来源。

备用快照不会生成原赛奖牌或奖线，不会把参考排名写入历史 CSV 的原赛排名列，也不会根据未经原赛验证的通过人数提前揭示 CCPC 题号。原有封榜和题号揭示机制继续生效。运行中的 VP 使用已加载的安装版本；升级及替换监控进程前先检查 tmux 和保存的 VP 状态并取得用户确认，继续沿用原站开始时间和个人提交记录。

## 数据与第三方组件

仓库和安装包不包含任何比赛数据。首次使用时自动获取，可识别的 ICPC / CCPC 区域赛从 [XCPCIO board-data](https://github.com/xcpcio/board-data) 读取正式参赛资格、奖牌配置和原赛提交记录，按学校、队名和成员身份与平台榜单匹配。资格校验通过、提交记录复算与终榜一致后，才保存相应缓存。

XCPCIO 尚未收录的 CCPC 区域赛，会尝试 [SRK Collection](https://github.com/algoux/srk-collection) 的公开原赛档案。SRK 档案须明确标记正式参赛资格，且题目链接与当前 QOJ 比赛的全部题目 ID 一致；提交记录须逐题复算并与 QOJ 公开终榜匹配，才启用赛时回放。学校、队名、成员等身份信息完全一致且仅有一份非空记录的换账号空记录会被排除；存在多份实际参赛记录时保留校验失败提示。

生成的数据保存在用户自己的 `~/.cache/vp/originals/`（设置 `XDG_CACHE_HOME` 时使用 `$XDG_CACHE_HOME/vp/originals/`），后续使用复用缓存。缓存可以删除，下次使用会重新获取；首次获取需要网络。不需要修改仓库或手动添加比赛 JSON 文件。无法取得完整可靠原赛数据的比赛，仍显示本人成绩和提交，并说明参考排名或统计缺失的原因。XCPCIO 的 MIT 许可证保留在 `third_party/xcpcio/LICENSE`。

SRK Collection 的档案按其 AGPL-3.0 许可证提供，来源和许可证保留在 `third_party/srk/`；仓库仅包含独立编写的档案读取器，不内置 SRK 比赛数据或组件代码。

提交器来自 [hikariyo 的 QOJ submit.py](https://gist.github.com/hikariyo/b3cec2e736d87be57d1e4faafb04f908) 与 [ehnryx/cf_submit](https://github.com/ehnryx/cf_submit)，固定版本、兼容补丁与现有许可证保存在 `third_party/`。Python 运行时的来源与校验值见 `runtimes/manifest.json`。

本仓库包含运行程序、安装依赖、使用文档与离线回归测试；比赛数据、账号配置及个人比赛文件不纳入仓库。测试仅使用内存中生成的虚构页面和临时文件，不读取真实 Firefox Cookie，不启动真实比赛 VP，不提交代码；真实网络被阻断，启动逻辑通过模拟 HTTP 响应执行。

## 同步原作者更新

本 Fork 的 `origin` 应指向 `CanDuanQi/vp-helper`，`upstream` 仅用于读取原仓库。首次设置：

```bash
git remote add upstream https://github.com/thedyingkai/vp-helper.git
git remote set-url --push upstream DISABLED
```

同步前确认 `git status` 干净，在保存本修改的分支上合并、解决可能的冲突并测试，然后仅推送自己的 Fork：

```bash
git fetch upstream
git merge upstream/main
.venv/bin/python -m unittest discover -s tests -v
git push origin HEAD
bash install-user.sh  # 使用系统安装的用户改用 bash install.sh，执行前确认 sudo 操作
```

不要用 `reset --hard upstream/main` 丢弃本 Fork 的修改，也不要向 upstream 推送或发起 PR。
